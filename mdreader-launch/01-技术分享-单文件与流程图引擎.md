# 我没重写 Mermaid，只在它前面加了一道判定

> 副标题：一个 3.8 MB 单文件 Markdown 阅读器里的四个工程决策
> 定位：技术复盘，不是产品软文。读者对象是想了解"单文件应用怎么落地"的前端/桌面端开发者。
> 建议投放：公众号首发 → 掘金（可加代码块）→ 知乎（改写成问答）。
> 全文约 4200 字，公众号阅读时长约 11 分钟。

---

运维同事发来一份 2000 行的《采集异常排查手册.md》，我要看的只是第三节的参数表。

打开 VS Code 要等插件加载、要建工作区；丢进在线 Markdown 编辑器，内网资料出网是合规红线；系统自带的预览是一整页黑字，滚三十屏找不到那个表。

这件事我解决得比较土：做了个本地阅读器，双击 `.md` 就开，一个 HTML 文件 3.8 MB，运行时不发任何网络请求。后来它长到了能看 1100 篇 Obsidian 笔记、能点表头排序、能画流程图，还做了 Windows 安装包和 iOS 主屏幕版。

今天不复述功能。我想讲四个当时必须做的工程决策，尤其是第三个——**关于 Mermaid，我最后悔没有更早做的决定，是决定"不重写它"**。

---

## 决策一：先把约束钉死，再谈架构

大多数"单文件应用"是结果，不是设计。它们通常是先写完代码，再想办法打包成一个文件，然后开始出现各种"线上好使本地不好使"。

我把顺序反过来了。第一条约束是：

**运行时零网络请求。** 这句话不是营销口号，是可以 grep 验证的工程约束——整个 `app.js` 里没有任何指向外部域的 `fetch` 或 `XMLHttpRequest`。

一旦接受这条约束，后面几乎是必然的：

| 约束推导 | 结果 |
|---|---|
| 不能从 CDN 加载依赖 | 三个 vendor 库必须内联进 HTML |
| 内联后体积会膨胀 | 必须放弃框架，用原生 JS（`app.js` 1834 行，无构建期转译） |
| 不能引用外部图片 | 品牌图标、皮肤图标、二维码、口号海报全部 base64 内嵌 |
| 不能有服务端 | 文件读取、编码识别、渲染、导出全部在浏览器或渲染进程内完成 |

结果是 3.78 MB。这个数字不好看，但它是**约束的诚实价格**：3.78 MB 换"任何内网机器、U 盘、断网环境都能打开"。对一个要在机房笔记本上用的工具，这笔交易划算。

反过来说，如果你的场景是公网 SaaS，这套取舍就完全不成立——**先定约束，再选架构**，顺序错了后面全是补丁。

---

## 决策二：构建脚本只做一件事

`build.py` 只有 99 行。它不做压缩、不做 tree-shaking、不做代码分割——它只做一件事：**把外部文件塞进一个 HTML**。

核心就三段。

第一段，内联 vendor：

```python
VENDORS = [
    ("marked.min.js", "marked.js v15"),
    ("hljs.min.js",   "highlight.js v11"),
    ("mermaid.min.js","mermaid v10"),
]

def inline_js(text: str) -> str:
    # 防止 vendor 代码中出现 </script> 提前闭合 script 标签
    return text.replace("</script", "<\\/script").replace("</SCRIPT", "<\\/SCRIPT")
```

那行 `</script>` 转义是踩出来的。highlight.js 里有处理 HTML 的字符串字面量，里面就带 `</script>`；不转义的话，内联进 `<script>` 标签会把标签提前闭合，页面从中间开始变成一堆文本。

第二段，内联二进制资源。图标和二维码走 base64，同时校验文件是否齐全：

```python
BRAND_TOKENS = {
    "__BRAND_LIGHT_DATA__": HERE / "brand-light.png",
    "__BRAND_DARK_DATA__":  HERE / "brand-dark.png",
    "__SKIN_LIGHT_DATA__":  HERE / "skin-light.png",
    ...
}
```

第三段，也是我认为最值钱的 3 行——**构建完做断言**：

```python
assert "__BRAND_" not in text, "品牌图标占位符未全部替换"
assert "__SKIN_" not in text,  "换肤图标占位符未全部替换"
assert "__SLOGAN_" not in text,"口号海报占位符未全部替换"
```

模板里用 `__BRAND_QR_DATA__` 这类占位符，替换漏了会静默输出一个带断图的 HTML——肉眼要翻到欢迎屏才看得见。加一行 `assert`，构建期直接炸。

> 经验：**构建脚本里最有价值的不是"做了什么"，是"没做完就报错"。** 静默失败的单文件构建，排查成本远高于多写一行断言。

顺带说个反例。这个项目最早是把构建产物也提交进仓库的（Electron 壳需要一个 `desktop/app/MDReader.html` 副本）。结果源码改了两轮，那份副本还停在旧版本——旧副本 4275 KB、没有多标签功能，新构建 3866 KB、有 9 处 `tabbar`。**贡献者 clone 下来 `electron .` 跑的就是旧界面，而 CI 一路绿灯。**

根因很简单：CI 跑完构建，没有检查工作区有没有变化。补上就两行：

```yaml
- name: 生成物漂移检查
  run: |
    git diff --exit-code -- MDReader/dist
    cmp MDReader/dist/MDReader.html MDReader/desktop/app/MDReader.html
```

**"构建成功"和"构建结果和仓库里的一致"是两件事。** 前者 CI 默认就会告诉你，后者必须自己加。

## 决策三：我不重写 Mermaid，只加一道判定

这是全文重点。

### 为什么不能直接用官方 Mermaid

第一版就是直接用的。问题很快暴露：

1. **换肤换不动。** 官方 Mermaid 运行时生成 SVG，颜色写死在元素的内联 `style` 和内部的 `<style>` 里。我有三套主题（浅色 / 深色 / 护眼）× 两套排版皮肤（卡片 / 纸张），六个组合都要配色。用官方主题变量能改一部分，但节点填充、边框、文字、连线标签总有几处不跟着走，切主题后会出现"深色画布上漂着几个白框"。
2. **做不了动效。** 我想让连线有方向流动感（排查手册里的数据流，静态箭头看不出先后），但官方 SVG 的结构我不能假定，加动画类名会随时被下个版本改掉。
3. **导出不可控。** 我要"单独下载这张图为 SVG"，官方给的是页面里的一个节点，样式依赖外部 CSS，导出去就散架。

### 关键判断：只有 20% 的语法需要特殊处理

真正的转折点是想清楚一件事：**Mermaid 的语法有几十种，但排查手册里 95% 的流程图只用到 6 种节点形状和 4 种箭头。**

于是我没有选择"实现 Mermaid"，而是选择"**实现一个能覆盖常见子集的渲染器，剩下的全部交还给官方**"。

判定就一个正则：

```javascript
var RISK_LINE = /^\s*(subgraph|end|classDef|class|style|linkStyle|click|direction|
  stateDiagram|classDiagram|sequenceDiagram|gantt|pie|mindmap|timeline|
  erDiagram|journey|gitGraph|quadrantChart|requirementDiagram|block-beta)\b/i;

function risky(src) {
  var ls = String(src).split(/\r?\n/);
  for (var i = 0; i < ls.length; i++) {
    if (RISK_LINE.test(ls[i])) return true;
    if (/:::|@\{|~~~|\bshape\b/.test(ls[i])) return true;
    if (/^\s*%%\{/.test(ls[i])) return true;   // 指令块
  }
  return false;
}
```

命中任何一行 → `risky = true` → **整块交回官方 Mermaid**，功能完整，只是样式跟随不到我的主题。
没命中 → 走自研渲染器，拿到完整控制权：跟随 CSS 变量换肤、连线流动动画、SVG 导出、复制为图片。

这个设计带来三个好处，都不是性能层面的：

- **正确性有兜底。** 我永远不需要为"这个语法我实现得对不对"负责，官方实现不了的东西我也不会更对。
- **维护成本低。** 新增语法时我什么都不用做，它会自动落到 `risky` 分支。
- **降级是静默的。** 用户不会看到报错，最坏情况是"这张图不能跟随深色主题"，而不是"这张图挂了"。

> 如果一开始就想着"做一个 Mermaid 替代品"，这个项目会死在第 40 种语法上。**做子集 + 显式降级，比做全集 + 悄悄出错，工程上划算得多。**

### 自研那部分：布局算法里只有一个真正的坑

自研渲染器 733 行，分四段：解析 → 布局 → 生成 SVG → 交互。

解析部分要处理的恶心事不少：一条线上有多个语句用 `;` 分隔，但 `;` 可能出现在节点文字里；节点文字里可能有 `[` `]`；13 种节点形状的括号组合（`[[子程序]]`、`[(圆柱)]`、`((圆))`、`([体育场])`、`{{六边形}}`、`{菱形}` …）。拆语句时要跟踪括号深度和引号状态：

```javascript
function splitStatements(line) {
  var out = [], buf = '', depth = 0, quoted = false;
  for (var i = 0; i < line.length; i++) {
    var ch = line[i];
    if (ch === '"') quoted = !quoted;
    if (!quoted && (ch === '[' || ch === '(' || ch === '{')) depth++;
    if (!quoted && (ch === ']' || ch === ')' || ch === '}')) depth--;
    if (ch === ';' && depth === 0 && !quoted) { out.push(buf); buf = ''; }
    else buf += ch;
  }
  ...
}
```

布局用经典的**最长路径分层**：拓扑排序，每个节点 `rank = max(前驱 rank) + 1`，然后同层节点按重心法迭代排序减少连线交叉。常量是这么定的：

```javascript
var GAP_MAIN = 86, GAP_CROSS = 44, PAD = 40, HEAD = 52, FOOT = 36, MIN_W = 124;
```

**这里有一个坑，我花了最久才定位。**

排查手册里的流程图经常有回路——"采集失败 → 重试 → 还是失败 → 回到重试"。有环的图不能直接拓扑排序，第一版我给环做了个"断环"处理，随便挑一条边断开。结果画板被拉成一条超长细条：因为断在哪条边是随机的，一旦断在主干上，某个节点的 `rank` 被推到十几层，整张图从 16:9 变成 1:12，缩放到能看全时字已经看不清了。

正解是用 DFS 三色标记**先识别回边，再算层级**：

```javascript
/* 先用 DFS 着色识别「回边 / 环路边」并从最长路径计算中排除，
   避免环（重试回路、回环）把节点层级推到画板最右、把画板拉成超长细条；
   被排除的回边在下方按 b.rank <= a.rank 判定为回边，走 U 形外侧通道路由。 */
var color = {}, backEdges = {};
function dfs(u) {
  color[u] = 1;
  adj[u].forEach(function (v) {
    if (v === u) return;
    if (!color[v]) dfs(v);
    else if (color[v] === 1) backEdges[u + '>' + v] = true;  // 指向祖先 = 回边
  });
  color[u] = 2;
}
```

指向"正在访问的祖先"的边就是回边。把它排除出 `rank` 计算，层级立刻正常；回边本身仍然要画，走图形外侧的 U 形通道绕过去。

**分层算法的质量，取决于你如何处理不合法的输入，而不是合法输入。** 无环图谁都能排好，有环图才是真实文档的样子。

第二个细节小但很影响观感：**文字宽度必须实测，不能估算**。

```javascript
function tw(s, font) {
  if (typeof document !== 'undefined') {
    try {
      if (!_ctx) _ctx = document.createElement('canvas').getContext('2d');
      _ctx.font = font || FONT_BOLD;
      return _ctx.measureText(s).width;
    } catch (e) { /* Node / 无 canvas 环境走估算 */ }
  }
  // 兜底估算：中文按 14px、大写字母 9.1、其余 7.7
  var w = 0;
  for (var i = 0; i < s.length; i++) {
    var c = s.charCodeAt(i);
    w += c > 0x2e80 ? 14 : (c >= 65 && c <= 90 ? 9.1 : 7.7);
  }
  return w;
}
```

节点边框是按文字宽度算出来的。用"字数 × 平均宽度"估算，中文混英文混数字时必然有几处文字顶破边框或者留一大片空白——尤其在 `{{六边形}}` 这种斜边形状里特别明显。`measureText` 一改，观感立刻从"手搓"变成"像那么回事"。

## 决策四：让纯文本也能变图，但不污染 Markdown 语义

排查手册里还有一种更土的情况：有人就是这么写的——

```
浏览器 → 负载均衡 → 应用网关 → 采集服务
                              ↘ 数据库
```

没有 Mermaid，就是几个箭头。让他改成 Mermaid 语法？他不会，也不该逼他学。

所以我做了第二层：**把带箭头的纯文本块转成 Mermaid 源码，再交给渲染器。**

两件事要做对。

第一件，**箭头归一化**。中文输入法打出来的箭头有十几种：`→ ⇒ ➜ ⟶ ➔ ⇏ ⇛ ⤳ ↘ ↗ ↓ ↑ ↔ ⇄ ⟷ ⇌`。用户不该知道哪些被支持。

```javascript
var ARROW_MAP = [ /* Unicode 箭头 → 统一形态 */ ];
function normArrows(s) { /* ... */ }
```

第二件，**配置不能塞进正文**。我想让用户能指定方向（`LR` / `TD`）和配色，但不想发明一套 Markdown 之外的新语法——文档还要能拿到别处正常显示。

解法是用 HTML 注释承载配置，注释在渲染后天然不可见，在别的编辑器里也不破坏语义：

```javascript
var HINT_RE = /@\/\/md-render-hint\/([\s\S]*?)@\/\/end-md-render-hint\/|<!--\s*md-render-hint\s*([\s\S]*?)-->/gi;
```

```markdown
<!-- md-render-hint direction=LR theme=accent -->
浏览器 → 网关 → 采集服务
<!-- /md-render-hint -->
```

同一条规则还有一个副作用很好用：**"转换态"是文档里的记忆，不是内存里的状态。** 顶栏点一次"流程图"按钮，全篇符合条件的代码块被替换成图形并打上标记；再次点击，按标记还原成原文。换主题、切排版、重新打开文件，转换态都还在——因为它是文档的一部分，不是编辑器的一个变量。

> 这条经验可以推广：**当你需要给用户文档加"元信息"时，优先用宿主格式已经允许的注释，别发明语法。** 你的工具可能只活 3 年，用户的文档要活 10 年。

## 复盘：做对的、做错的

### 做对的三件

1. **先钉约束。** 零网络请求这条一句话约束，替我否决了后面 90% 的架构选择，省掉无数"要不要引入 XX"的讨论。
2. **子集 + 显式降级。** 不追求覆盖全集，命中风险语法就交回官方。这让 733 行代码撑起了一个"看起来完整"的能力面。
3. **构建期断言 + CI 漂移检查。** 产物和源码不一致这类问题，靠人眼永远发现不了，只能靠 `assert` 和 `git diff --exit-code`。

### 做错的三件（都是真实踩过的）

1. **把生成物提交进了仓库。** 结果仓库里躺着一份落后两个版本的界面，而且 CI 绿灯。**生成物要么不进仓库，要么进了就必须有漂移检查，没有第三种选项。**
2. **构建输出目录没固定。** 打包脚本每次往新目录写，半年攒了 20 多个 `release-new*`，每个 475 MB，本地仓库一度到 11 GB。清理后是 18 MB。**构建产物必须有固定输出路径 + gitignore，这条要在项目第一天定。**
3. **文档里写了"把 OWNER 替换成你的用户名"。** 这句话在别人 fork 之后照着做，会把自家仓库的所有链接改坏。**面向贡献者的文档里，不要出现"你自己改一下就好了"的步骤**——那是给未来的自己挖坑。

### 一个数字

单文件 3.78 MB，其中 mermaid 一个库就占 3.2 MB。也就是说，如果砍掉流程图能力，体积能降到 0.6 MB。

我没砍，因为"文档里有流程图"和"文档里只有代码块"，在排查手册这种场景里是完全不同的可读性。**但这是个明确的、可以量化的取舍，不是一个"没办法"的结果**——如果你的用户不需要图，那 0.6 MB 的方案明显更好。

## 最后

这个项目没有一行后端代码，没有一个 npm 依赖（`app.js` 是手写的原生 JS），构建脚本 99 行 Python 标准库。

它证明不了什么宏大的事。但它证明了：**一个约束清晰的小工具，可以把工程细节做到和大项目一样的严谨度**——可复现构建、产物漂移检查、第三方许可清单、零网络的自我验证命令。

如果你也在维护"给自己用的小工具"，我的建议只有一句：

> **先写下你不能妥协的那一条约束，然后让所有技术选型向它低头。** 剩下的，都是细节。

**讲的时候容易被追问的三个问题，提前准备**：

1. *"为什么不直接做成 VS Code 插件？"* —— 目标用户不装 VS Code；插件仍要开编辑器；文件关联做不到双击即开。
2. *"3.8 MB 的 HTML 打开不慢吗？"* —— 冷启动实测约 0.4–0.8 秒（本地文件，无网络）；比 IDE 快一个量级；大文档的瓶颈在渲染不在解析。
3. *"自研渲染器维护成本会不会失控？"* —— 不会，因为降级是显式的；新增语法自动落到官方分支，我只维护 6 种形状 + 4 种箭头。
